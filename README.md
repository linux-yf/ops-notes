## 两条维护规则

1. **Inbox 定期清空**：每周花点时间把 00-Inbox 里的碎片归档进对应目录；归档动作本身就是二次加工，正是知识内化的过程
2. **目录宁缺毋滥**：只建当前用得上的目录。比如现在还没用到 RDMA，就别先建 `network/rdma/`，等真出现第一篇相关笔记再细分



##运维工作大纲
一、故障案例库（核心）
五要素模板：现象描述 → 排查过程 → 根因 → 解决方案 → 预防措施
记录时机：故障解决后立即用语音备忘录口述关键步骤（避免拖延），每日下班前花几分钟整理碎片，周末做本周聚合

推荐字段结构：
故障标题：建议格式为"系统名+故障类型+关键现象"，如"vLLM 副本显存 OOM 导致推理服务 503"——标题必须包含具体症状关键词，而不是笼统的"系统异常处理"
故障现象（一句话）+ 影响范围（一句话）
排查过程：按时间顺序列表，命令与输出对照呈现，重点说明"看到什么结果意味着什么"
根因分析、处理步骤（含可执行命令）、验证方式（如何确认已恢复）、防范措施
关键结论前置：让读者不必读完全文就能找到命令

二、操作手册与标准化文档（RunBook / SOP）
RunBook：安装、部署、备份、调优，每做一次就完善一次，遇到问题不再到处搜索
SOP：把模型上线、节点初始化、副本扩缩容等流程标准化，交给新人也能完美执行
场景化应对手册：某个标签的记录积累到多条时，升级为应对手册，如《显存溢出应急指南》含命令树、清理优先级、自动化巡检脚本片段
关键调优参数
自动化脚本：思考日常的工作能否用自动化脚本解决
项目档案：每个项目记录架构图、方案选型、风险点和经验教训；项目结束，一份完整资料直接可以写进简历

三、数据档案（用数据说话的能力）
会用数据汇报本周、本月的平台数据

四、行业与技术情报（保持敏锐度）
大模型运维的技术栈迭代极快，需要持续追踪
岗位要求风向：定期看 AI 平台运维类招聘 JD，能直接看到市场在要什么——目前招聘要求已涵盖 GPU 服务器与算力调度、vLLM 等推理框架、RAG 与向量数据库运维、AI 可观测体系建设、Token 管理与模型路由等
官方文档与一手资料：遇到新工具先读官方 Getting Started，再精读架构部分——第一手资料永远最权威
社区故障案例：逛 GitHub issue、技术社区看别人的排障案例，很多你卡几天的问题别人一句话就能点醒
